=== F5/F6 최종 실측 결과 (2026-09-05) ===

## F5: Renode ElapsedCycles 기반 WCET (전체데이터셋 모델)

측정 방법: sysbus.cpu ExecutedInstructions(명령어 수) 기반 추정(CPI 1~2 가정)을 폐기하고,
Renode 공식 사이클 카운터 프로퍼티 sysbus.cpu ElapsedCycles로 직접 실측.

| 클래스 | 사이클/회 | 명령어/회 | 사이클/명령어 비율 | 168MHz 기준 시간 |
|--------|-----------|-----------|---------------------|-------------------|
| R      | 627,304   | 69,666    | 9.00x               | 3.73ms            |
| DoS    | 551,659   | 54,821    | 10.06x              | 3.28ms            |
| Fuzzy  | 908,880   | 51,657    | 17.59x (최악/WCET)  | 5.41ms            |
| RPM    | 456,632   | 58,439    | 7.81x               | 2.72ms            |
| gear   | 366,978   | 60,139    | 6.10x               | 2.18ms            |

요구사항(<=10ms) 대비 최악(Fuzzy) 기준 1.85배 여유.
※ 사이클/명령어 비율이 클래스마다 6.1~17.6배로 상이 - 소프트웨어 부동소수점(double) 에뮬레이션
  비용이 명령어 종류에 따라 다르게 반영된 것으로 추정. 이전 "명령어수 x CPI 1~2 가정" 방식
  (0.31~0.83ms)은 실측 대비 5배 이상 과소평가였음.

## F6: 실제 bxCAN 하드웨어 FIFO 오버런 검증

환경: STM32F4 실제 bxCAN 페리페럴(CAN1, 레지스터 레벨 MCR/MSR/RF0R/필터뱅크)을 처음부터
초기화하는 드라이버 직접 작성. Renode의 emulation CreateCANHub + machine
CreateSocketCANBridge로 리눅스 vcan1 <-> 에뮬레이션된 실제 CAN 페리페럴을 연결.
호스트에서 cansend로 보낸 진짜 CAN 프레임이 실제 하드웨어 레지스터 경로를 거쳐
IDS 코드까지 도달하는 end-to-end 파이프라인 구축.

5,000건 집중 전송 대조 실험:

| 조건                              | 오버런(FOVR0) 발생 |
|-----------------------------------|---------------------|
| DRAIN_FIFO=0 (일부러 방치)        | 4,979 / 5,000건      |
| DRAIN_FIFO=1 (IDS 정상 운영)      | 0 / 5,000건          |

결론: 베이스라인(미처리)에서는 거의 전량 오버런 발생을 확인했고, IDS가 실시간으로
FIFO를 비우며 처리하면 동일 부하에서 오버런이 완전히 사라짐을 실측으로 증명.
"IDS 처리 속도가 실제 CAN 버스 부하를 감당해 프레임 누락을 막는다"는 인과관계를
시뮬레이션(리눅스 vcan + Renode 에뮬레이션 실제 CAN 페리페럴)으로 직접 검증.

남은 한계: 수 시간 단위 장시간 연속운용은 미검증(수천 건 단위 집중부하까지만 수행).
